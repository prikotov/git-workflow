# План релиза v0.4.3

## Метаданные

- Тег релиза: `v0.4.3`
- Тип повышения версии: `patch`
- Обоснование выбранной версии: исправление поставляемого workflow-шаблона (`fix(ci)`) — устойчивость шага Collect PR content к транзиентным сбоям GitHub API; PHP-код валидатора и init-скрипта не менялся, обратно совместимо
- База рабочей ветки: `master` (`53c0c31`)
- Рабочая ветка: `release/0.4.3`
- PR подготовки релиза в основную ветку: [#17](https://github.com/prikotov/git-workflow/pull/17)
- Ответственный: владелец проекта
- Плановая дата публикации: 2026-11-13

## Состав

- Включённый PR: [#16](https://github.com/prikotov/git-workflow/pull/16)
- Источник: инцидент проекта-потребителя TasK ([run 43238563578](https://github.com/prikotov/TasK/actions/runs/43238563578)): GitHub API вернул plain-text ответ, `gh api --jq '.title'` упал на JSON-парсинге (`invalid character 'S'`), шаг Collect PR content (`set -euo pipefail`, без retry) уронил scan на единичном хиккапе
- `templates/workflows/secret-scan-pr-content.yml`: `api_retry` для обязательных вызовов title/body — 3 попытки, backoff 2s/4s; финальная неудача роняет шаг с текстом ошибки API в логе (stderr последней попытки не подавлен); комментарии остаются опциональными (`|| true`); script-injection защита не тронута (контент `gh → файл`, не в команду)
- Верификация: порт байт-идентичен проверенному фиксу потребителя ([TasK PR #3193](https://github.com/prikotov/TasK/pull/3193), смержен `c04c464ee`; ревью DevOps-ревьювера — 4 mock-сценария под `set -euo pipefail`; ре-ран упавшего workflow зелёный)

## Риски

- Проекты-потребители получат фикс только после повторного запуска `bin/git-workflow-init --force` — существующие копии workflow без `--force` не перезаписываются; до переинициализации локальная правка потребителя (если сделана) остаётся действенной.
- Изменение одного YAML-шаблона: PHP-код, init-скрипт, документация конвенций не затронуты.
- Миграции данных и переменные окружения отсутствуют.

## Порядок публикации

1. Слить PR из `release/0.4.3` в `master` после успешного CI и одобрения.
2. Проверить совпадение содержимого одобренной ветки и коммита слияния.
3. Создать и отправить аннотированный тег `v0.4.3` на проверенный коммит слияния.
4. Создать GitHub Release по существующему тегу.

## Проверки перед публикацией

- `composer validate --strict`
- CI репозитория успешен
- Проверка относительных Markdown-ссылок и `git diff --check`
- Тег и ветка выпуска до начала подготовки свободны

## Действия при проблеме после релиза

- Откат потребителя: локальная правка workflow (патч из TasK PR #3193) без обновления пакета; пакетный откат — patch-релиз `v0.4.4` с revert-коммитом по [регламенту hotfix](../../git-workflow/release-checklists.md).
